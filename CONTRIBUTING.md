# Contributing to the Copilot Ramp Playbook

Thanks for your interest in helping! This is an **unofficial, community-built** project — a guided
on-ramp through the Microsoft Copilot maturity journey, written by people who use these products every
day. It is **not** affiliated with, endorsed by, or an official resource of Microsoft.

The whole point of this repo (versus everyone making their own copy) is that **multiple folks can
collaborate on one shared playbook**. PRs, issues, and discussions are welcome.

By contributing, you agree to:

- Follow the [Code of Conduct](CODE_OF_CONDUCT.md).
- License your contributions under this project's dual license:
  **code/tooling → MIT** ([`LICENSE`](LICENSE)) · **written content under `docs/` → CC BY 4.0**
  ([`LICENSE-CONTENT.md`](LICENSE-CONTENT.md)).

---

## What you can contribute

- **Walkthroughs** — new use cases, or filling out an existing stub. Walkthroughs are the heart of the
  site.
- **Content fixes** — typos, broken links, outdated screenshots, terminology drift, clearer wording.
- **Resources** — new entries in `docs/RESOURCES.md` (verified official Microsoft links).
- **Tooling / build** — improvements to `tooling/`, the QA guard, the screenshot tool, or the MkDocs
  config.
- **Issues / discussions** — request a walkthrough, report something inaccurate, or propose a change
  before doing the work.

If you're not sure where something fits, open an issue first and we'll point you at the right place.

## Local setup

You need **Python 3.12+** (and **Node 20+** if you're working on the screenshot tool).

```bash
git clone https://github.com/<your-org>/copilot-ramp-playbook.git
cd copilot-ramp-playbook

pip install -r requirements.txt

# Live preview at http://127.0.0.1:8000
mkdocs serve
```

`mkdocs serve` rebuilds on save, so you can edit Markdown and watch the page update.

To produce the static site exactly the way CI does:

```bash
mkdocs build --strict     # --strict fails on broken internal links
```

The Playwright screenshot tool is a separate npm package under `tooling/screenshots/` — see
[`tooling/screenshots/README.md`](tooling/screenshots/README.md) (or the package itself) for setup. You
only need it if you're capturing or refreshing screenshots.

## The contribution flow

We use the standard branch → PR → review → merge flow. Direct pushes to `main` are blocked.

1. **Pick something to work on** — an existing issue, or open one describing what you want to do.
2. **Branch off `main`** with a short, descriptive name:
   `walkthrough/<slug>`, `fix/<slug>`, `tooling/<slug>`.
3. **Make your changes locally** and preview them with `mkdocs serve`.
4. **Run the checks CI will run** (see "Required checks" below) so the PR comes in green.
5. **Open a pull request** against `main`. Fill out the PR template — it's short and exists to keep
   reviews fast.
6. **Address review feedback.** A maintainer (per [`CODEOWNERS`](.github/CODEOWNERS)) will be
   auto-requested.
7. **Merge** — once approved and green, a maintainer will merge. The site **auto-deploys** to GitHub
   Pages from `main`.

### Required checks (run these locally before opening a PR)

CI runs these on every PR; you can run the same commands locally:

```bash
python tooling/qa/check-content.py   # stdlib content QA guard
mkdocs build --strict                # fails on broken internal links
```

If either fails, fix it before requesting review.

## Adding or expanding a walkthrough

Walkthroughs are the centerpiece of the site. They follow a **locked content model** so the experience
feels consistent across 70+ pages.

**Read first:** [`CONTENT-MODEL.md`](CONTENT-MODEL.md) — frontmatter schema, the rich-walkthrough
template, and authoring rules. This is the source of truth.

**Then look at:** the exemplar — `docs/walkthroughs/chat-meeting-followups.md`. New walkthroughs should
match its shape.

In short, every walkthrough needs:

- Correct **frontmatter** (title, description, stage, roles, updated date, tags).
- The **standard sections** in the standard order (intro, when to use, prereqs, steps, prompt, what to
  expect, troubleshooting, next steps, related).
- **Copy-pasteable prompts** — a reader should be able to grab and use them.
- **Honest screenshots** — see the next section.
- A bumped `updated:` date in the frontmatter.

### Two-state screenshot honesty rule

Walkthrough images are one of two states — **never anything in between:**

1. **Real captures** generated by the Playwright tool under `tooling/screenshots/` and committed under
   `docs/screenshots/<slug>/` (preferred when feasible).
2. **An honest no-screenshot note** that explains why and points the reader at the numbered written
   steps we keep current.

We **never** ship faked, mocked, stale, or AI-generated UI screenshots. If a real capture isn't
available, the no-screenshot note is the correct answer — the QA guard checks for this.

## Style & quality bar

A few things we care about (a longer style guide is on the roadmap):

- **Honest about limits.** If a feature is preview, license-gated, region-limited, or behind admin
  controls, say so plainly.
- **Practical voice.** We're talking to busy practitioners — clear, direct, second person ("you").
- **Correct product names.** "Microsoft 365 Copilot," "Copilot Chat," "Copilot Studio," "Microsoft
  Foundry." Capitalize as Microsoft does.
- **Useful link text.** No naked URLs and no "click here" — the link text should describe the target.
- **Fresh `updated:` dates.** When you meaningfully edit a page, bump the date.

The QA guard catches some of this automatically; reviewers will catch the rest.

## Reviews & merging

- Every PR needs **at least one maintainer approval** (CODEOWNERS auto-requests review).
- The `ci` status check must be **green** before merge.
- Maintainers may request changes for content-model conformance, accuracy, tone, or scope.
- We prefer **squash-merge** with a short, imperative commit subject.

---

## Governance (short version)

- **Maintainers** review and merge PRs and steward the content model. See [`MAINTAINERS.md`](MAINTAINERS.md).
- Decisions are made in the open, on issues and PRs, by rough consensus among maintainers.
- Big direction changes (new top-level sections, scope, name, license) are discussed in an issue
  first.
- Becoming a maintainer is described in [`MAINTAINERS.md`](MAINTAINERS.md).
